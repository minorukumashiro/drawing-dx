# estimate-helper（見積もり類似実績検索ツール）

見積もり自動化ツール。新しい引き合い（径・材質・得意先）を入力すると、

- **図面DXプラットフォーム**（このリポジトリの Firebase Firestore、`workspaces/default` の `drawings[]`）
- **弥生販売25**（「元帳印刷」画面からエクスポートした得意先元帳・仕入先元帳のテキスト）

の両方から「似たような過去実績」を横断検索し、単価の目安（一覧・平均・中央値・レンジ）を出します。

- **第一段**（本ページ前半）: このディレクトリのCLI (`node bin/estimate.js ...`) で手元から検索する
- **第二段**（[後半セクション](#第二段-firestore同期--図面dx画面の類似実績検索ボタン)）: 弥生データをFirestoreの新規コレクション`yayoiRecords`に取り込み、`index.html`（図面DX本体）の図面詳細画面に「💰 類似実績検索」ボタンとして統合したもの
- `mail-fax-watcher/` と同じ構成の独立したNode.jsツールです（このツール専用に `npm install` が必要）
- **Firestoreへの書き込みは `bin/import-to-firestore.js` のみが行います**（新規コレクション`yayoiRecords`のみ）。CLI (`bin/estimate.js`) と図面DX本体のブラウザ側コードは常に読み取り専用です。図面DX本体の`workspaces/default`ドキュメントには一切触れません（1ドキュメント1MB制限に達して壊れるのを避けるため、弥生データは別コレクションに分離しています）

---

## セットアップ

```bash
cd estimate-helper
npm install
cp config.example.json config.json
```

`config.json` を開いて環境に合わせて編集します（`config.json` は `.gitignore` 対象なので、書き込んでもリポジトリにコミットされません）。

### 1. Firestoreの認証情報

`serviceAccountKeyPath` で `mail-fax-watcher/serviceAccountKey.json` を指すよう設定します（デフォルトで `../mail-fax-watcher/serviceAccountKey.json` を指しています。同じ鍵を読み取り専用で流用しているだけなので、既に `mail-fax-watcher` をセットアップ済みならそのままで動きます）。**このツールはFirestoreに対してread（get）しか行いません。**

### 2. 弥生の元帳データ

`config.json` の `yayoiFiles` に、弥生から書き出したテキストファイルのパスと種別（`customer`=得意先元帳 / `supplier`=仕入先元帳）を書きます。`data/` フォルダにコピーして相対パスで指定してもいいですし、下記の実例のようにOneDrive等の元の場所を直接指定しても構いません。

```json
"yayoiFiles": [
  { "path": "C:\\Users\\yourname\\Documents\\Yayoi\\Exchange\\Shimt.txt", "type": "supplier" },
  { "path": "C:\\Users\\yourname\\Documents\\Yayoi\\Exchange\\Tokmt.txt", "type": "customer" }
]
```

## 弥生からのエクスポート手順（実機で確認済み・2026-07-24）

弥生販売25には元帳データを直接取得するAPIが無いため、手作業でエクスポートしたファイルを読み込む方式です。**「ファイル」→「Excelへの書き出し」ではなく、「元帳印刷」画面の「エクスポート」ボタンを使います。**

1. 弥生販売25で対象の元帳（**得意先元帳** または **仕入先元帳**）の「元帳印刷」画面を開く
2. 対象の得意先/仕入先を1社選び、期間を指定して表示する
3. 画面の **「エクスポート」** ボタンを押す
4. 既定の出力先はユーザーの `Documents\Yayoi\Exchange\` フォルダ（環境によっては `OneDrive\ドキュメント\Yayoi\Exchange\` 等、Documentsの実体がある場所）。ファイル名は種別ごとに固定で、**仕入先元帳＝`Shimt.txt`、得意先元帳＝おそらく`Tokmt.txt`**（同フォルダに前回分が残っていると上書きされるので、別の得意先/仕入先ごとに残したい場合はエクスポート後に別名で `estimate-helper/data/` 等へコピーしておくこと）

> 実際に `Shimt.txt`（仕入先元帳、対象1社分）をエクスポートして中身を確認済みです。以下の「読み込みの仕組み」はこの実データに基づいています。得意先元帳側もほぼ同じ列構成であることをサンプル(`Tokmt.txt`、住所欄が続く分だけ列が多い)で確認していますが、そのサンプルは古い可能性があるため、**得意先元帳を初めて使う際は一度エクスポートし直して、`--json`オプションで生データを見ながら列位置(後述の`yayoiFieldIndex`)がずれていないか確認してください。**

## 読み込みの仕組みと実際のフォーマット

`lib/yayoiSource.js` が担当します。

- 拡張子は `.txt`。**見出し行はありません**。1行 = 1明細（またはメモ・入金・消費税などの1行）で、カンマ区切り・全フィールドダブルクォート囲みの固定位置CSVです
- 文字コードは **Shift_JIS(cp932)**（既定値。UTF-8で書き出された場合は該当ファイルの設定に `"encoding": "utf8"` を追加すれば読めます）
- **1ファイル＝1取引先**（元帳印刷で1社ずつ表示してエクスポートする運用のため）。ただし各行にも取引先名が入っているため、ファイル名には依存しません

実データで確認できた列位置（0始まり。`config.json` の `yayoiFieldIndex` で上書き可能）：

| 列番号 | 内容 | 備考 |
|---|---|---|
| 3 | 日付 | `YYYYMMDD`（例: `20090220`） |
| 4 | 伝票番号 | |
| 14 | 行区分 | `1`=商品/取引の実明細行、`99`=消費税、`2`/`3`=入金・振込・手数料等、`5`=金額を伴わないメモ行 |
| 17 | 摘要 | 品名・仕様。**材質記号やφ径はここに書かれている**（例: `2/4　チューブ　φ70×φ85×1918Ｌ`） |
| 19 | 単位 | |
| 23 | 数量 | |
| 24 | 単価 | |
| 25 | 金額 | |
| 30 | 見積番号 | 入っている場合のみ |
| 39 | 取引先名 | フルネーム。得意先元帳はこの後ろに住所・電話番号等が続く（列数が増えるだけで位置は変わらない） |

**実績データとして採用する行**は「行区分(14)が`1"`かつ金額(25)が正の値」の行だけです。値引・振込・手数料・消費税・メモ行は単価の目安を歪めるため自動的に除外します（`lib/yayoiSource.js`の`ADMIN_DESC_RE`および金額>0の条件）。

摘要のテキストから **材質コード**（SUS304, SS400, SCM435 等）と **径**（`φ80`のような表記）を正規表現で自動抽出します。これは `index.html` のOCR自動読取り（`parseOCR`）・類似検索（`calcSimilarity`）と同じロジックを流用しています（`lib/extract.js`）。パイプ・チューブ材の「13C」のような略記は現状の材質パターンには含まれていないため、その場合は材質が「-」（未検出）のまま径・得意先だけでマッチします。

### 列位置がずれていた場合

弥生のバージョンや元帳の種類によって列位置が変わる可能性があります。ずれていそうな場合は次の手順で調整してください。

1. `node bin/estimate.js --no-firestore --json --diameter 1` のように条件を1つだけ指定して実行し、結果の `raw` 配列（生の列データ）を確認する
2. 目的の値（日付・摘要・数量・単価・金額・取引先名）が何列目にあるか数える
3. `config.json` の `yayoiFieldIndex` の該当項目だけ数値を書き換える（他は既定値のままでOK）

### オプション一覧

| オプション | 説明 |
|---|---|
| `-d, --diameter <mm>` | 径(mm)。図面の「φ80」の80の部分 |
| `-m, --material <code>` | 材質コード（例: `SUS304`, `SS400`） |
| `-c, --client <name>` | 得意先名（図面DX表記・弥生表記どちらでもOK。「（株）」「株式会社」等の法人格表記の違いは自動で吸収。masterタブの「弥生 得意先突合」で紐づけ済みの表記ゆれも考慮） |

| `--top <n>` | 上位n件を表示（既定: `config.json`の`defaultTop`、なければ15） |
| `--min-score <n>` | このスコア(0-100)未満を除外（既定: `config.json`の`defaultMinScore`、なければ40） |
| `--tolerance <r>` | 径の許容比率。既定0.2（±20%） |
| `--source <name>` | `all`(既定) / `drawing-dx` / `yayoi-customer` / `yayoi-supplier` |
| `--config <path>` | `config.json`のパス（既定: `./config.json`） |
| `--json` | 結果をJSONで出力（列位置調整時のデバッグや他ツール連携用） |
| `--no-firestore` | 図面DX(Firestore)を読み込まない |
| `--no-yayoi` | 弥生データを読み込まない |

検索条件（`--diameter` / `--material` / `--client` / `--size`）は1つ以上あればよく、指定した項目だけでスコアを計算します（例: 材質のみ指定すれば材質一致度だけでランキング）。

## 類似度スコアの考え方

`lib/similarity.js`。`index.html` の `calcSimilarity()`（図面同士の類似検索）と同じ考え方を、
「入力条件が部分的（径だけ・材質だけ等）でも公平に比較できる」よう調整したものです。

- **径の近さ**（配点40）: 比率が許容幅(既定±20%)のさらに1/4以内ならほぼ満点、許容幅以内なら高得点、許容幅の2倍以内でも少し加点
  - 実績側にφ表記が無い場合は、摘要中の最大の数値を代表寸法として比較（`index.html`と同じフォールバック）
- **材質の一致/類似**（配点35）: 完全一致→満点、同じ材質グループ（SUS304系・SS400系など）→7割、頭2文字が同じ→4割
- **得意先の一致**（配点25）: 表記一致（法人格表記の違いは吸収）、部分一致、または masterタブで紐づけ済みの弥生名⇔図面DX名が一致すれば満点

入力条件に無い項目（例: 得意先を指定しなかった場合の得意先軸）は配点から除外し、残りの配点だけで100点満点に正規化します。そのため「材質のみ一致」でもスコアが高く出ることがあります — 表内の「マッチ理由」列で何が根拠になっているかを必ず確認してください。

## データの更新のしかた（CLI利用時）

- **図面DX(Firestore)側**：常に最新をその場で読みに行くため、更新作業は不要（実行するたびに最新の`drawings[]`を取得）
- **弥生側**：新しい取引が増えたら、弥生の「元帳印刷」→「エクスポート」を再実行してファイルを上書き（またはコピー先を分けて`config.json`の`yayoiFiles`に追記）するだけで、次回実行時から反映されます

## 制限事項・今後の調整予定（CLI・パーサー共通）

- 得意先元帳側の列位置は、確認済みの仕入先元帳(`Shimt.txt`)と同じという前提です。実際に得意先元帳をエクスポートしてズレがあれば `config.json` の `yayoiFieldIndex` を調整してください（手順は上記「列位置がずれていた場合」参照）
- 材質・径の抽出は正規表現ベースの簡易推定です（`lib/extract.js`）。JIS規格外の社内呼称（「ALH」等）はJIS材質コードとしては抽出できませんが、`lib/similarity.js`/`index.html`側の類似度計算では摘要テキストへの部分一致でフォールバックするため、`--material ALH`のような検索自体は機能します
- 伝票種別(`yayoiFieldIndex.voucherKubun`、既定は列5)が仕入伝票"14"・売上伝票"24"以外（支払・入金伝票等）の行は実績として取り込みません。`yayoiItemVoucherKubuns`で調整可能です

## 第二段: Firestore同期 + 図面DX画面の「類似実績検索」ボタン

CLIと同じ検索ロジックを、図面DX本体（`../index.html`）の画面から直接使えるようにしたものです。

### アーキテクチャ

```
弥生 元帳印刷→エクスポート (Shimt.txt / Tokmt.txt 等)
        │  node bin/import-to-firestore.js （手動実行・管理者権限で書き込み）
        ▼
Firestore コレクション「yayoiRecords」（1件=1ドキュメント、読み取り専用でブラウザから参照）
        │
        ▼
index.html の図面詳細画面「💰 類似実績検索」ボタン
  → yayoiRecords を径・材質で絞り込みクエリ + drawings[]（ブラウザに読み込み済み）をその場でスコアリング
  → 単価目安・類似実績一覧を表示
```

**`workspaces/default`（図面DX本体のドキュメント）には一切触れません。** 弥生データを本体ドキュメントに混ぜるとFirestoreの1ドキュメント1MB制限にすぐ到達して同期が壊れるため、`yayoiRecords`という完全に独立したコレクション（1件=1ドキュメント）に分離しています。Firestoreはドキュメント数が多いことには強いので、この形なら数万〜数十万件でも問題ありません。

### `yayoiRecords` コレクションのフィールド

| フィールド | 型 | 内容 |
|---|---|---|
| `source` | string | `yayoi-customer` / `yayoi-supplier` |
| `partnerCode` | string | 弥生の取引先コード |
| `voucherNo` / `lineNo` | string | 伝票番号・明細行番号（年度で振り直されるためIDには日付も併用） |
| `date` | string\|null | `YYYY-MM-DD` |
| `client` | string | 得意先/仕入先名（弥生の表記そのまま） |
| `material` | string | 摘要から抽出したJIS材質コード（無ければ空文字） |
| `diameterMm` | number\|null | 摘要の`φ`表記から抽出した径(mm) |
| `sizeRaw` / `name` | string | 摘要の原文 |
| `qty` / `unitPrice` / `amount` | number\|null | 数量・単価・金額 |
| `quoteNo` | string | 見積番号（あれば） |
| `updatedAt` | Timestamp | インポート日時（サーバー時刻） |

ドキュメントIDは `${source}_${取引先コード}_{日付}_{伝票番号}_{明細行番号}` で、同じ取引は何度再インポートしても同じIDになります（＝再実行しても重複登録されない、upsert方式）。

### インポートスクリプトの使い方

```bash
cd estimate-helper
node bin/import-to-firestore.js --dry-run   # 書き込まずに件数・サンプルだけ確認
node bin/import-to-firestore.js             # 実際にFirestoreへupsert
```

`config.json` の `yayoiFiles` に設定した弥生エクスポートファイルを全て読み込み、`lib/yayoiSource.js`（CLIと共通）で実績行を抽出して `yayoiRecords` コレクションへ書き込みます。

### 運用: 弥生データの更新は手動です

**弥生データはリアルタイム連携していません。** 新しい取引を検索対象に含めたい場合は、そのつど次の手順が必要です。

1. 弥生販売25で対象の得意先/仕入先の「元帳印刷」→「エクスポート」を実行し、`Documents\Yayoi\Exchange\` 配下のファイル（`Tokmt.txt`/`Shimt.txt`）を上書き、または別名で保存
2. 新しい取引先を追加する場合は `estimate-helper/config.json` の `yayoiFiles` にファイルパスを追記
3. `node bin/import-to-firestore.js` を実行してFirestoreに反映

（図面DX本体側の`drawings[]`は今まで通りリアルタイム同期のままです。ボタンを押すたびに最新のものを見に行きます。）

### 複合インデックス

`firestore.indexes.json`（リポジトリルート）に以下を定義し、`firebase deploy --only firestore:indexes` で反映済みです。

```json
{
  "collectionGroup": "yayoiRecords",
  "fields": [
    { "fieldPath": "material", "order": "ASCENDING" },
    { "fieldPath": "diameterMm", "order": "ASCENDING" }
  ]
}
```

必要な理由: ブラウザ側は「材質が一致する範囲で、径が近い順」に絞り込むクエリ（`where('material','==',...).where('diameterMm','>=',lo).where('diameterMm','<=',hi).orderBy('diameterMm')`）を投げます。Firestoreは等価条件(`material`)＋範囲条件(`diameterMm`)の組み合わせに複合インデックスを要求するため。径のみ・材質のみの単独クエリは自動生成される単一フィールドインデックスで足りるため、追加の複合インデックスは不要です。

もし将来「得意先で絞り込みつつ径の近さで並べる」等の新しいクエリパターンを追加する場合は、同様に `firestore.indexes.json` に追記して再デプロイしてください（デプロイしないと該当クエリはFirestoreからエラーで拒否され、エラーメッセージ内のリンクから必要なインデックス定義を確認できます）。

### ブラウザ側の使い方

1. 図面DX（`index.html`）にログインし、任意の図面カードをクリックして詳細画面を開く
2. 「💰 類似実績検索」ボタンを押す
3. その図面のサイズ（φ表記があれば径、なければサイズ文字列）・材質・取引先を条件に、`yayoiRecords`（Firestore、読み取り専用）と`drawings[]`（登録済み図面、その場でスコアリングするだけでFirestore書き込みは発生しない）を横断検索し、スコア順の一覧と単価目安（件数・平均・中央値・レンジ）をモーダルで表示する
4. 結果はスコア順（径の近さ・材質一致/類似・得意先一致で重み付け、CLIの`lib/similarity.js`と同じロジック）。行の「マッチ理由」列でスコアの根拠を確認できる
5. クエリはFirestoreの範囲・複合インデックスを使い、径がある場合は対象径から見て近い順に上下それぞれ最大150件（計最大300件）だけ取得する設計（全件をブラウザに持ってこない）。レイテンシは1〜3秒程度を想定

### 制限事項（ブラウザ機能側）

- 得意先の絞り込みはFirestore上では完全一致でしか行えません（表記ゆれの吸収はローカルに取得できた候補に対してのみ行われます）。径・材質が図面に登録されていない場合、得意先のみでの絞り込みになり、ヒット率が下がることがあります
- 径・材質のどちらも図面に登録が無い場合は`yayoiRecords`側の検索ができず、`drawings[]`側のみでの結果になります
- JIS規格外の材質呼称（「ALH」等）は材質での絞り込みクエリ自体はできません（Firestore上は`material`フィールドが空のため）。この場合は径だけで候補を取得し、摘要テキストへの部分一致でスコアリングします（CLIと同じ挙動）
